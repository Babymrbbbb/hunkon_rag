# 从 83% 到 100%：一个 RAG 知识库评测体系的可靠性实战

> 定位：技术类文章（RAG、LLMOps、评测体系、可靠性工程）
> 作者视角：47 家门店连锁 AI 落地负责人，自研 RAG 知识库与评测门禁的一手复盘
> 数据说明：所有通过率、用例数、修复过程均来自生产知识库真实评测记录（2026-10-27 至 2026-11-01），可回溯

---

## 引子：评测通过率「不可信」，比通过率低更可怕

我们维护着一个生产环境的 RAG 知识库：1,600+ 篇业务资料编译为 1,700+ 页可导航知识，支撑门店员工自然语言查询供应链、门店标准、营销活动。为了保证检索链路改坏了能及时发现，我们建了 **24 条评测用例**，覆盖权威口径、竞品、防幻觉、品牌、运营、产品、行业、供应链、加盟、聚合层、口语化 11 类场景，并且定了一条铁律：**凡改检索链路，必须跑全量回归，通过率必须 100%。**

但很快发现一个尴尬的问题：**评测通过率本身不可信。**

某天运行全量评测，24 例全部显示「⏭ 限流跳过」。看起来是上游模型 API 配额不足，属于基础设施问题，不是知识库质量出问题。但当我们深入排查，发现了一个更隐蔽的事实——**「限流跳过」可能掩盖了真正的代码 bug。**

这篇文章记录我们如何把评测通过率从 **83.3% → 91.7% → 24/24（100%）**，以及过程中踩到的五个坑。这五个坑，任何一个都可能让你误以为「系统是好的」。

---

## 第一层：基础设施失败 ≠ 质量失败

评测门禁跑在真实 LLM 调用之上，而上游 API 经常不稳定（429 限流、503 冷却）。如果把这些「基础设施失败」算作评测失败，通过率会持续误报，门禁就失去了意义。

我们的第一个设计：`is_infra_failure()`——识别 429 / 503 / ERROR 类响应，标记为「⏭ 限流跳过」，**从通过率分母剔除**。这个设计本身是对的，但它埋下了一个隐患：**如果代码里抛出的不是质量错误，而是 NameError，也会被误判为「限流跳过」。**

某天运行评测，24 例全部「限流跳过」。日志里全是 `ERROR`，`is_infra_failure()` 全部命中，看起来完全正常——「上游又限流了」。但我们后来发现，真正的根因是：

```
rag_qa.py 第 527/555 行调用 FAST_MODE()
但函数定义是 _fast_mode()（第 511 行）
→ NameError: name 'FAST_MODE' is not defined
```

**24 例全部「限流跳过」的真正根因不是限流，而是一个函数名拼写错误。**

这个 bug 的可怕之处在于：`is_infra_failure()` 太聪明了，它把 NameError 也吞进了「基础设施失败」里。评测链路看起来在跑，实际一行代码都没执行到。**「基础设施失败 ≠ 质量失败」是对的，但必须确保只有真正的基础设施错误才被豁免。**

修复：两处 `FAST_MODE()` → `_fast_mode()`。修复后立即有 1 例真实通过，证明链路通了。

> **经验 1**：豁免逻辑要保守。只有确认是网络/配额/限流类错误才允许跳过；任何代码异常（NameError、TypeError）都不应被豁免，否则评测会「假跑」。

## 第二层：口语化检索根治——「店里一共多少家」答成 40 家

评测通过率恢复到真实值后，我们看到了真实的失败。最刺眼的一类：**口语化用例 0/2**。

用户问：「店里一共多少家？」
知识库回答：「40 家。」

正确答案应该是 **47 家**（权威口径：清远含连州 40 家 / 广州含花都 4 家 / 肇庆 2 家 / 佛山 1 家）。为什么答错？

**根因不在 LLM，在检索。**

`wiki_search` 默认做字面匹配。当问题里出现「天鹅公主」这个实体词时，检索能命中权威聚合页 `entity/天鹅公主.md`，LLM 读到权威口径，回答正确。但口语化问题「店里一共多少家」**不含实体词**——字面匹配不到权威聚合页，LLM 只能拿到旧资料（清远含连州 40 家），于是答成「40 家」。

这是一个典型的 RAG 检索质量问题：**关键词证据太弱时，权威聚合页进不了上下文。**

我们做了三层修复：

### 1. 检索层：语义触发词兜底

在 `wiki_search` 增加语义触发词映射——当问题命中「门店 / 多少家 / 分布 / 哪些城市」等口语化词时，自动补充权威实体 `entity:天鹅公主` 作为兜底查询。这样即使问题不含品牌实体词，权威聚合页也能进入候选集。

### 2. 内容层：聚合页口径修正

检查 `entity/天鹅公主.md` 聚合页，发现 5 处旧口径把「40 家」写成了总数。逐处修正为「47 家（权威口径）」，lint 校验 89/89 通过。

### 3. 代码层：重编时自动修正

只在页面层修正还不够——知识库每日增量编译，旧资料可能再次把错误口径编入聚合页。所以在 `kb_rules.py`（权威规则模块）增加一条规则：**重编时自动修正「运营 40 家门店」→「47 家」**。这样即使源头资料又出现旧口径，编译产物也会被规则修正。

> **经验 2**：RAG 答错，先查检索，不要怪 LLM。口语化问法（不含实体词）是检索召回的头号杀手，语义触发词兜底是低成本高收益的修复。

## 第三层：评测词表边界——「合理拒绝」被判失败

通过率从 83.3% 升到 91.7% 后，还剩 4 例失败。逐一分析，发现其中 2 例是**评测词表边界问题**，不是知识库质量问题：

1. **创始人问题**：知识库回答「未明确提及」（合理诚实拒绝），但评测的 `GRACE_TOKENS` 列表里没有「未明确提及」这个词，导致合理回答被判失败。
2. **慕斯保质期问题**：回答内容合理，但评测要求 `must_include=['市场']`，而正确答案里没有出现「市场」这个词。

这两例本质是**评测用例写得太死**——把「可选产物」当成了「必需字段」。我们做了两处修正：

- `GRACE_TOKENS` 补充：「未收录 / 未记载 / 未明确提及 / 未查到」——合理拒绝不再误判
- 放宽 `must_include`：保质期类问题只要求包含「保质期」，不再要求不相关的高频词

> **经验 3**：评测词表边界和用例断言要基于「正常样本的字段分布」来定，只把「全都有」的列为必需。否则评测会惩罚合理行为，产生假失败。

## 第四层：权威闸收敛为共享模块——多入口系统防规则漂移

知识库系统有**多个编译入口**：`build_wiki.py` 负责每日增量编译，`generate_agg_pages.py` 负责聚合页重编。最初，权威口径的修正规则 `_apply_ruling_overrides()` 在两个文件里各有一份**逐字符相同的复制粘贴实现**。

复制粘贴的隐患：改了一处，忘了另一处，两个入口行为漂移。某个入口编译出的页面不经过权威修正，评测就能发现口径错误——但更危险的是**评测没覆盖到的场景**。

我们做了一次重构：把 `_apply_ruling_overrides` 抽取为**共享模块 `kb_rules.py`**（`apply_ruling_overrides`，零第三方依赖），两个入口都改为 `import` 复用，删除本地拷贝。重构后用功能等价单测验证：玛芝莲口径正确降级（🔴→🟡 + 33 家澄清）、天鹅公主无 33 家原样保留；双入口 dry-run 均正常。

> **经验 4**：多入口系统的规则必须放在共享位置，两处 import 复用，而不是复制粘贴。改完要做三步自检：grep 确认所有入口有调用 → 逐入口单测 → 端到端实跑。

## 第五层：知识治理——待验证项 80 → 0 的分级闭环

评测通过率 100% 之后，我们继续做知识库治理。lint 巡检发现 80 条「待验证项」——这些是历史积累的存疑内容（门店数口径、竞品信息、供应商报价等）。如果不处理，它们会一直留在知识库里，成为潜在的「错误事实源」。

我们做了三件事：

1. **修复 lint 报告截断**：`pending_review[:50]` 只展示前 50 条，后 30 条被隐藏。去掉三处截断，报告完整展示全部待验证项。
2. **异常队列核销**：31 条历史「HTTP 503 编译失败」存量记录，页面已修复，批量标记「已核销」。
3. **待验证项分级闭环**：80 条按 P0/P1/P2 分级处理——
   - **P0（7 条）全部查证闭环**：天鹅公主门店数 → 以裁决 47 家为准；法大吉 → 16 城 60+ 店；玛芝莲 → 现场核验 ≥10 家；金粒门融资 → 市场传闻未官宣；百度一见 → 无公开硬门槛
   - **P1（19 条）**：4 条公开查证 + 15 条内部数据类转「待回填」
   - **P2（48 条）**：公开查证 / 脏数据删除 / 观察项 / 模拟数据隔离声明保留

最终：待验证 **80 → 0**，锚定 3598/3598（100%），死链/孤立/冲突全部 0。

> **经验 5**：知识库可信度治理要分级。外部可查证的（POI/公开报道）优先查证闭环，内部数据类转「待回填」，模拟数据隔离声明是安全警示不应删除——但 lint 不应把它计为待验证项（这是另一个误报修复）。

## 结果：24/24（100%）的完整链路

修复完成后，全量评测最终结果：

| 类别 | 结果 |
|---|---|
| 权威口径 | 3/3 ✅ |
| 竞品 | 3/3 ✅ |
| 品牌 / 运营 / 行业 / 供应链 / 加盟 / 聚合层 | 12/12 ✅ |
| 产品 | 3/4 → 修正词表后 4/4 ✅ |
| 防幻觉 | 1/2 → 修正词表后 2/2 ✅ |
| 口语化 | 0/2 → 语义触发词兜底后 2/2 ✅ |
| **总计** | **24/24（100%）** |

评测通过率 100% 不是终点——它意味着：**当评测说「通过」时，我们可以相信这个结论。** 这比数字本身更重要。

---

## 总结：评测体系可靠的五个要点

1. **豁免逻辑要保守**：只有真正的网络/配额错误才允许跳过，代码异常绝不豁免——否则评测会「假跑」。
2. **答错先查检索**：口语化问法（不含实体词）是 RAG 召回的头号杀手，语义触发词兜底是低成本高收益修复。
3. **评测词表要贴近真实分布**：只把「全都有」的字段列为必需，合理拒绝不应误判。
4. **多入口系统的规则要共享**：复制粘贴 = 规则漂移，共享模块 + import 复用 + 逐入口验证。
5. **知识治理要分级**：外部可查证的查证闭环，内部数据类待回填，安全警示保留但不要误计为质量问题。

一个可靠的评测体系，不是「通过率 100%」这个数字，而是**每一层失败都能被正确归因**。做到这一点，评测门禁才能真正成为知识库发布的守护者。

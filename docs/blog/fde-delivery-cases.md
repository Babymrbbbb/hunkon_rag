# 一次连锁 AI 落地，拆成 3 个可复用的交付案例

> 定位：技术/商业交叉类文章（AI 落地、解决方案交付、零售数字化）
> 本文只描述方法论、架构取舍、评测方法与工程判断，不含任何真实品牌信息、经营数据或个人身份叙事；文中数据与示例均为合成演示数据。
> 说明：文中不给出未经核实的量化指标；验证以仓库内可复现的评测与检索探针为准

---

## 为什么要把项目「拆成案例」

AI 落地项目最常见的汇报方式是「上线了 6 类 AI 应用」。但真正做过交付的人知道，这种说法有两个问题：

1. **不可验证**——「6 类应用」听起来像堆砌，读者无法判断系统到底做了什么
2. **不可复用**——项目结束了，方法论没沉淀下来，下一个项目从零开始

更好的做法：**把一个项目拆成多个标准化交付案例**。每个案例遵循同样的结构：业务痛点 → 需求访谈 → 方案设计 → PoC → 试点 → 上线 → 量化结果 → 复盘。

下面用 3 个标准化交付案例说明方法论。

---

## 案例 1：统一数据底座

**业务痛点**：工厂 ERP、门店收银、公域平台（抖音/美团）、私域 SCRM 四条数据源各说各话；同一个数在三个系统三个值；经营分析靠人工 Excel 汇总，决策慢半拍。

**需求访谈**：和总部确认目标——建成 12 家门店统一数据链路；经营分析次日自动生成；确立关键事实唯一真相源。

**方案设计**：先统一主数据（门店编码/SKU/会员 ID 一码通），再打通四条数据源，最后才谈 AI。关键决策：唯一真相源（冲突以裁决为准）+ 日清日结。

**PoC**：先打通 1 条数据链路（门店收银 → ERP → 经营分析），验证「次日自动生成」可行性。

**试点上线**：3 家门店 + 1 个区域运营组灰度，培训店长，迭代报表格式。

**工程结论**：以评测用例、检索探针与全量回归验证链路；量化成效需实际实施后统计，本文不给出未经核实的数字。

**复盘沉淀**：
- 测试绿 ≠ 线上对（必须加检索探针 + 全量回归）
- 关键事实唯一真相源（旧口径显式标注已过时）
- 空输入比报错更危险（有效源数 ≥1 前置校验）

## 案例 2：RAG 知识库

**业务痛点**：员工查标准/活动/供应链靠翻文档，资料散落各处；总部被重复问询占用大量人力。

**需求访谈**：确认目标——员工用自然语言查标准/查活动/查供应链；覆盖多类业务场景；答案可评测、可回归。

**方案设计**：原始资料不可直接检索，先做「业务知识编译层」（清洗、结构化）再输入 RAG。采用倒排 + 向量 RRF 双路召回。配套评测用例集作为发布门禁。

**PoC**：选 2 个场景（门店标准、活动查询）验证流水线 + 双路召回效果。

**试点上线**：5 家门店试点，收集查询失败案例迭代，再扩至 12 家。

**工程结论**：以评测用例、检索探针与全量回归验证链路；量化成效需实际实施后统计，本文不给出未经核实的数字。

**复盘沉淀**：
- 通过率太高反而是危险信号（执行与验收必须分离）
- 让 AI 审查 AI 要防「走过场」（无异议通过率 >50% 触发告警）
- LLM 会截断长文件名（路径解析必须校验存在性 + 兜底）

## 案例 3：模型网关 + 任务编排

**业务痛点**：批量自动化 AI 任务依赖单一模型 API，限流/故障会导致全部失败；成本不可控；无熔断降级；无额度隔离。

**需求访谈**：目标——批量任务稳定运行；多模型池化调度；按业务风险划分能力池。

**方案设计**：自研零依赖 OpenAI 兼容模型网关，多账号池化 + 自动切换 + 熔断降级 + 额度隔离。

**PoC**：接 3 条任务（经营分析/内容生产/行业研究）验证网关可用性 + 限流切换。

**试点上线**：经营分析 + 内容生产两条链路灰度，监控稳定性。

**工程结论**：以评测用例、检索探针与全量回归验证链路；量化成效需实际实施后统计，本文不给出未经核实的数字。

**复盘沉淀**：
- 免费档限流陷阱（多账号池化 + 慢速模式）
- 基础设施失败 ≠ 质量失败（429/503 应从评测分母剔除）
- 降级链要真实注入（配置了必须在 prompt 里真正用，端到端实跑确认）

## 可复用交付方法论

三个案例背后是同一套五步法：

1. **先统一数据口径**——动手前先解决「同一个数三个系统三个值」
2. **再拆解人的动作**——把真实操作者每天做的事写下来
3. **判断哪些能交出去**——纯搬运和套规则的交给 AI
4. **最后才选工具**——按任务价值分层选模型
5. **嵌入日常 + 对结果负责**——使用方验收、使用度量、零使用预警

这套方法不限于烘焙。零售、餐饮、本地生活、制造——只要数据可信，AI 就能落地。

---

## 结尾

AI 落地项目要「可复用」，不是靠记住几个数字，而是靠把每个项目拆成**结构化的交付案例**。每个案例沉淀出可复用的模板、测试集、机制——这才是解决方案工程师的核心资产。

数据底座是案例 1，知识库是案例 2，模型网关是案例 3。三个案例拼起来，就是一套覆盖「数据 → 知识 → 模型」的完整交付体系。

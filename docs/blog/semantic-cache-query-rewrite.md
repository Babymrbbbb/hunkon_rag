# 语义缓存与查询改写：RAG 生产级化的最后两块拼图

> 本文只描述方法论、架构取舍、评测方法与工程判断，不含任何真实品牌信息、经营数据或个人身份叙事；文中数据与示例均为合成演示数据。

## 背景：为什么补这两块

此前的文章已讨论 Langfuse 采样监控与 RAGAS 四指标量化。但对照市面生产级 RAG 方案（RAGFlow / Dify / FastGPT 等），仍有两块明显缺口：

1. **语义缓存**：对语义等价的重复问题直接返回历史答案，跳过 LLM 调用。市场数据显示可节省 60%+ LLM 成本、响应快数十倍。
2. **查询改写**：口语化/指代不明/缺实体的问法先经 LLM 改写为检索友好形式，可提升召回 10-20%。

本文记录这两项能力的零依赖实现。

## 一、语义缓存：SQLite + 余弦相似度

### 设计约束

- **零第三方依赖**：生产知识库长期保持纯标准库（避免与既有环境冲突），因此不用 `redis`、`numpy`，只用 `sqlite3` + 纯 Python 余弦。
- **默认开启但可关**：`KB_SEMANTIC_CACHE=0` 关闭时零开销。
- **阈值可配**：`KB_CACHE_THRESHOLD` 控制命中严格度（默认 0.95）。

### 命中判定

用户问题先经向量化（`_embed_query`），与缓存中历史问题向量计算余弦相似度：

```python
def _cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb) if na and nb else 0.0
```

相似度 ≥ 阈值即命中，直接返回历史答案与引用；未命中则走完整链路，生成后写入缓存。

### 存储设计

SQLite 表 `semantic_cache`：

| 字段 | 说明 |
|---|---|
| `query_vec` | 查询向量（JSON 文本） |
| `question` | 原始问题 |
| `answer` | 历史答案 |
| `citations` | 引用列表（JSON） |
| `created_at` | 创建时间（用于 TTL 清理） |
| `hit_count` | 命中计数（供分析） |

### 关键细节

- **TTL 清理**：每次初始化时删除过期条目（默认 7 天），避免缓存膨胀。
- **命中计数**：每次命中 `hit_count + 1` 并记录 `last_hit_at`，后续可分析高频问题。
- **错误答案不缓存**：HTTP 错误、429、无 key 等失败响应绝不写入缓存。

## 二、查询改写：LLM 改写 + 质量校验 + 静默降级

### 设计约束

- **默认关闭**（`KB_QUERY_REWRITE=0`）：当前知识库聚合层已有「语义兜底」覆盖口语化问法，改写可能引入噪声。机制保留，供知识库规模扩大后开启。
- **静默降级**：任何异常/限流/校验不过，一律降级为原始查询，绝不阻塞主链路。
- **改写结果缓存**：避免重复调用 LLM（SQLite，7 天）。

### 工作流程

```
用户提问
  ↓
_looks_rewritable() 判断是否需要改写（口语词/指代词/短问法）
  ↓ 需要
LLM 生成改写（提示词：最小改写、保留实词、禁止反问句）
  ↓
_keeps_core_terms() 质量校验（数字/品牌/窗口词必须保留）
  ↓ 不过关
降级为原始查询（并覆盖缓存，防止坏改写残留）
```

### 质量校验：拦截「丢意图」的坏改写

初版改写提示词引导模型「补全实体」，但实测模型把「店里一共多少家？」改写成了**反问句**：

> 请问您指的是哪个品牌或店铺？请提供具体名称以便查询门店数量。

这种改写完全丢失了查询意图。为此实现 `_keeps_core_terms()` 质量校验：

1. **数字必须保留**（如门店总数、分布数、比例）
2. **品牌名必须保留**（演示品牌 / 竞品乙 / 竞品甲 / 示例主体）
3. **2-3 字窗口词至少一个保留**（用滑动窗口提取，避免整段贪婪匹配）

```python
def _keeps_core_terms(original, rewritten):
    nums = re.findall(r"\d+(?:\.\d+)?", original)
    for n in nums:
        if n in rewritten:
            return True
    for brand in ("演示品牌", "竞品乙", "演示主体", "延小保"):
        if brand in original and brand in rewritten:
            return True
    text = re.sub(r"[^\u4e00-\u9fff]", "", original)
    windows = set()
    for size in (3, 2):
        for i in range(len(text) - size + 1):
            w = text[i:i + size]
            if w not in _STOPWORDS:
                windows.add(w)
    return any(w in rewritten for w in windows)
```

### 一个值得记录的 bug：坏改写会残留在缓存里

修复质量校验后首次验证仍失败——排查发现是**改写缓存**里存了初版的坏改写，缓存命中时跳过了校验。修复：缓存命中同样过质量校验，不过关则覆盖为原文。

## 四、生产链路全景

```
用户提问
  ↓
[查询改写]（默认关，可开）→ 改写为检索友好问法（失败降级原文）
  ↓
[语义缓存]（默认开）→ 命中直接返回历史答案
  ↓
[聚合层语义兜底] → 口语化问法兜底命中权威聚合页
  ↓
[混合检索 RRF + 精排] → 倒排 + 向量融合
  ↓
[LLM 生成 + Langfuse 埋点] → 答案 + 引用
  ↓
[写入语义缓存]
```

## 五、经验沉淀

1. **生产级能力优先「零依赖」**：纯标准库实现语义缓存与查询改写，避免引入版本冲突，也便于部署。
2. **LLM 改写必须质量校验**：LLM 生成内容不可信，必须用确定性规则拦截坏改写，不能只靠提示词。
3. **缓存也要过校验**：坏结果一旦写入缓存会持续污染，缓存命中路径必须与写入路径同等的质量检查。
4. **默认稳定优先**：新能力默认关闭或低风险开启，先保证生产链路稳定，再逐步放开。
5. **可配置、可降级**：所有新能力都有开关和环境变量，异常时静默降级，绝不阻塞主链路。
